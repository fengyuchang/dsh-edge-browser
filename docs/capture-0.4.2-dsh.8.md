# 0.4.2-dsh.8：后台截图渲染保活

dsh.7 的日常实测已确认版本对齐、零视口恢复、语义定位和批量操作可用，仍报告后台首次截图可能超时；当时视口为正数，后续截图正常。dsh.8 针对普通截图的后台渲染路径做了加强，并细化超时说明。

## 改动

既有长截图已用小尺寸渲染流维持后台合成帧，普通视口截图此前未采用。现在普通截图也按请求获取这个共享占用，实际 PNG 仍来自原有 `Page.captureScreenshot`，保持完整尺寸。它不选择标签、不恢复或激活窗口，不隐藏控制条或光晕，也不通过等待截图去拖慢所有会话的启动。

已有录屏继续共享同一个流及帧确认机制。截图只释放自己的占用；已有消费者仍在时，保留其流及原有配置。获取、捕获与清理继续受时间、取消、任务归属、调试连接及文档身份检查约束；取消或页面变化后不发布迟到图片、不自动重放动作。普通截图的 10 秒总预算保持，超时文字会标明读取身份、准备后台渲染、抓取像素或核验文档等阶段。

Chromium 的截图实现明确依赖合成帧，并处理完全隐藏页面的特殊情况；维持脚本运行与维持截图合成帧是两个条件。[Chromium 截图实现](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/devtools/protocol/page_handler.cc) · [CDP Page 协议](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Page.pdl)。

## 验证

3,733 项扩展测试通过（425 跳过），721 项原生插件测试通过（10 跳过），两端类型检查通过。针对性测试覆盖后台无合成帧、共享录屏流不被截图收尾中断、准备期间归属变化，以及取消后不继续迟到图片。[公开验证数据](validation-0.4.2-dsh.8.json)。

独立 headless 与原生 Windows Edge 的 8 个新会话，首个截图均通过，耗时 `122–544 ms`。原生窗口放在非活动 Windows 桌面，启动采用 `--no-startup-window`，两种环境都未传 `--window-size`。任务页始终最小化。条件包括自然尺寸、导航前归零请求、导航后实际归零恢复和显式准备动画帧；导航前归零请求不等于导航后的视口仍为零，准备过动画帧也不称为完全未绘制。每次截图均记录到一次共享渲染获取和一次释放。

原有 42 项零视口、版本、合集、协作、人工接手、批量取消、空闲复用、跳转和读取取消验收通过。8 次点击截图采样 `368` 帧，光晕/控制条隐藏与移除均为 0。五组监测共 `266` 次采样，未检测到测试进程在用户桌面显示窗口或取得前台焦点。已有录屏共享由单元测试验证，本轮未操作用户的真实录屏或其他插件。

## 适用范围

**原 `.7` 在这些隔离条件下的基线截图也成功，尚未自然复现报告中的首次截图超时。** 本轮属于针对已发现路径缺口的渲染改进，仍需在原日常场景复验；不做通用提速倍数或“首截问题已彻底消失”的声明。单元测试中的“没有保活即没有帧”条件也不算自然复现。若再次超时，新版阶段说明可进一步定位。

跳转后提示旧读取仍在 Chrome 中等待时，原生调用必须先落定。这项保护继续保留；本轮没有证据表明每次跳转后的首次同步都会失败，不能用重放点击或无条件刷新来减少往返。技能的恢复参考补充了截图阶段的解释：同页且没有旧读取在途时，可仅重试截图一次；持续失败则报告图像不可用，依赖视觉的步骤等待处理，可独立完成的 DOM 读取继续。

## 更新

备份并更新两端，等当前任务结束后重新加载 Edge 扩展及 Harness BrowserSkill。关开插件后若运行版本仍旧，应从系统托盘正常退出 Harness 再重开。用运行状态和 `diagnose` 核对 `.8`；已确认新版的 Edge 无需重复重载。CLI / 协议仍为 `0.4.2 / 1.8`。
